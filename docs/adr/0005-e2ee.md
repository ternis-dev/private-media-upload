# ADR 0005 — E2EE: AES-256-GCM PWF1 containers, server blind (M3)

- Status: accepted (2026-10-08)
- Context: placement tiers (L1/L2/L3) control *where* bytes live, but a curious
  operator/admin can still read content. E2EE removes content visibility entirely.

## Decisions
1. **Cipher:** AES-256-GCM via WebCrypto (browser) / node:crypto (tests), 256-bit
   random key per file, 96-bit random nonce base, per-chunk nonce = base XOR
   BE64(index). 4 MiB chunks. Spec: `docs/e2ee-format.md`.
2. **Key transport = URL fragment** (`#k=<base64url>`): never sent to any server
   by construction. Key loss = data loss (stated in UI, no recovery).
3. **Manifest inside ciphertext:** chunk 0 = encrypted JSON
   (filename/mime/size) — server learns nothing, not even the filename.
   Stored asset keeps client-declared name only as an opaque label for the
   *container* (`secret.txt.pwf1`, `application/octet-stream`).
4. **Server is flag-blind by design:** API stores `e2ee: true`, skips mime-sniff
   and inline AV on flagged uploads; quarantine records skip (`scanned=2`).
   Server tests assert ciphertext opaqueness (stored bytes == uploaded bytes,
   no plaintext) rather than crypto correctness (client-tested).
5. **E2EE composes** with password/max-views/burn (defense in depth) and all
   tiers. E2EE + burn on L2/L3 is the strongest offered combination.
6. **Limits (honest):** ≤1 GB per E2EE file until streaming decrypt; no
   server-side malware scanning of ciphertext (R7); thumbnails impossible on
   ciphertext (deferred: client-generated thumbnail chunk, M4).

## Consequences
- `assets.e2ee` column (+auto-migration); `meta.e2ee`; openapi 0.4.0-M3.
- Web: upload toggle + share-page decrypt-from-fragment; `/me` export of E2EE
  assets yields ciphertext (owner must keep keys).
